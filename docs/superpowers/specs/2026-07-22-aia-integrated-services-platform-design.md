# AIA Integrated Services Platform Design

## Product identity and approved scope

This document specifies the approved evolution of the Tong Class website into the Beijing University Artificial Intelligence Institute Integrated Services System. The public product name is Artificial Intelligence Agora, abbreviated as AIA. Its approved English subtitle is “The Integrated Services Platform of PKU IAI”, and its Chinese name is “北京大学人工智能研究院综合服务系统”.

The supplied PKU IAI horizontal lockup is the initial logo source. The implementation will retain the existing navy-oriented interaction palette, use the logo red for institutional identity and emphasis, and use warm light surfaces for the public site. The complete lockup is reserved for sufficiently wide, light-background areas such as the hero and footer. Navigation uses a cropped AIA seal plus accessible live text rather than shrinking the whole raster lockup until it becomes illegible. A future official reverse logo may be used on dark surfaces after it is provided; the implementation will not recolor the supplied lockup with CSS filters.

The system has three user-facing domains. AIA is the new institute-level root site. Tong Class becomes an intact first-level undergraduate topic site. Admin, Reviewer, and TechDay remain independent product boundaries because they include private or external-audience workflows. AIA provides navigation and authorization bridges without folding these workflows into a single shell.

The first delivery contains the AIA information architecture, secure identity and authorization foundation, a directory backed by clearly marked demonstration teachers, graduate students, and research groups, and a real Coffee Talk application flow. It also establishes the reusable scope, notification, and workflow models needed by later OA, reimbursement, events, and content features. The initial delivery does not implement a West Building reservation system beyond a disabled “筹备中” card. It also does not connect WeChat Official Accounts or a mini program. Those channels are explicitly deferred until the in-app permission and notification core is stable.

## Architectural approach

The selected presentation direction is the AIA “academic gateway”. The root page presents AIA institutional identity, research, people, and current activity while making key services immediately reachable. It does not become a generic dashboard whose value depends on a future task system, and it does not reduce the institute to an editorial research showcase. The responsive design uses a single AIA navigation layer on desktop, a compact mobile menu, one page-level H1, accessible buttons and inputs, and no automatically advancing hero carousel.

The application is split into four explicit contexts. The AIA shell owns institute metadata, navigation, public footer, shared brand assets, and public institute pages. The Tong Class shell owns the undergraduate topic site, retaining its distinct navigation context and familiar content. The private product shells own Admin, Reviewer, and TechDay layouts. A shared client boundary in `src/lib/api.ts` remains the sole component-facing Convex integration point; components do not invoke raw Convex functions.

The following route tree is canonical.

```text
/                                  AIA root homepage
/institute                         institute profile and research directions
/people                            faculty, graduate students, and research groups
/people/[slug]                     public person profile
/groups                            research group directory
/groups/[slug]                     public research group profile
/research                          institute publication and research surfaces
/updates                           AIA news and notifications intended for the public
/services                          service directory
/services/coffee-talk              Coffee Talk programme overview
/services/coffee-talk/apply        Coffee Talk application
/services/coffee-talk/my           applicant and teacher status views
/contact                           office and administrative contacts
/tong-class/*                      undergraduate topic site
/account                           future personal workbench and notifications
/admin/*                           administrative product, not public
/reviewer/*                        academic-exchange reviewer product, not public
/techday/*                         TechDay product, including external audiences
```

Existing Tong Class public paths migrate to matching canonical `/tong-class/*` paths through a single redirect. The mapping includes `/about`, `/members`, `/users`, `/news`, `/publications`, `/resources`, `/courses`, `/events`, and `/intranet` plus their detail routes. Query parameters, especially `next`, search filters, and action identifiers, are preserved. API, Admin, Reviewer, and TechDay routes do not move in this migration. The old root path cannot retain its previous content because it becomes the AIA root; the new AIA hero and navigation provide a prominent Tong Class entry. Redirects begin as temporary during the migration verification window and become permanent only after analytics, login return paths, and external links are verified. No redirect chains are permitted.

Root metadata becomes AIA metadata with a title template, canonical URLs, social metadata, and a declared metadata base. A `/tong-class` layout overrides its title and description with Tong Class branding. Public detail pages receive server-generated metadata when their public DTOs are introduced. Sitemaps include only canonical public AIA and Tong Class pages. All intranet, admin, reviewer, account, authentication, search, and other private paths are excluded from sitemaps and marked `noindex`; robots metadata supplements but never replaces access control.

## Account, person, and organization model

An account, an institutional person, and a research-group membership are separate concepts. This avoids treating a teacher as a student merely to display them publicly and avoids using a system administrator role as an academic identity.

The existing `users` table remains the authentication and authorization account table. Its existing `role` field retains the compatible access-level values `member`, `admin`, and `super_admin`. Source code may call this conceptual value `accessRole`, but the initial migration does not rename the persisted field. A user receives a new independent `identityType` of `undergrad`, `graduate`, `teacher`, or `other`, along with an `accountStatus` of `active` or `disabled`. Student-specific fields are made optional where necessary for future teacher and staff accounts; existing student values remain unchanged. Administrative accounts retain their existing access role and receive an identity type only after a controlled administrative review. No identity is inferred from being an admin.

The migration of existing accounts is additive and idempotent. Every user with `role === "member"` and no identity type becomes `undergrad`. The migration never overwrites a nonempty identity type. It also establishes `accountStatus: "active"` only if no status is set. Every execution reports scanned, created, updated, skipped, and conflict counts. It uses natural keys and cursor batches, not a one-time flag, so a failed batch can safely be re-run. The migration is a standalone manually invoked operation and is never coupled to build, development, or start scripts.

The public institute directory is stored separately from login accounts. `institutePeople` stores a stable slug, public Chinese and English names, kind, title, biography, photo, research areas, approved public links, optional public email, visibility, and an optional `accountUserId`. `researchGroups` stores a stable slug, bilingual name, summary, long description, leader, research areas, links, recruitment information, visibility, and display order. `researchGroupMemberships` maps people to groups with a role, primary-group flag, dates, visibility, and sort order. A teacher or graduate student can therefore appear publicly without a login account, while a verified account can later be explicitly linked to the person record.

`publicationAuthorships` and `contentMentions` provide explicit people and group relationships for publications and news. Existing Tong Class publication ownership and encoded author references remain compatible inputs during migration. New institute aggregation never guesses from a name or a title. It uses a structured link, an existing linked account, or a curated alias. Group publication feeds are projections, not copied publication records, and deduplicate by DOI where available or by normalized title and year otherwise.

Public account queries are replaced by public DTO queries that return only allowed profile fields. Current-user and administrative queries are separate endpoints. Public responses never include student ID, institutional email, personal email, access role, account status, verification state, timestamps that reveal account status, sessions, or credentials. Private documents and attachments move out of the public directory and are served through authenticated short-lived download paths.

## Authorization and scope model

Authentication, authorization, and user management are enforced on the server. Every sensitive query and mutation resolves its actor from a valid session; no endpoint trusts a client-provided requester ID, role, owner ID, target organization, or user ID for authorization. The default policy is deny. A component may use a capability query to improve interface affordances, but the matching Convex query or mutation repeats the decision independently.

Public self-registration is removed at the backend boundary, not only hidden in the interface. Account creation, disabling, password reset, identity changes, access-role changes, and account deletion or soft-disable are controlled administrative operations with audit records. The initial account provisioning flow is administrator-created and invitation-oriented. A privileged role cannot be requested in a registration payload. The last active super administrator cannot be disabled, deleted, or demoted. Existing destructive seed, default-credential, and debug functions are removed from reachable development deployments or strictly restricted to explicitly approved local-only tooling.

The authorization model combines system groups and explicit grants. System groups include `identity.undergrad`, `identity.graduate`, `identity.teacher`, `identity.other`, `role.admin`, and `role.super_admin`. `accessGroups` supports later custom groups. `accessGroupMembers` records identity-derived, role-derived, or manually granted membership. `accessRules` assigns an explicit resource and action to a user or group at global, organization, owner, or object scope. Rules are centrally whitelisted rather than allowing arbitrary strings or wildcard permissions. The authorization evaluator applies a super-administrator recovery bypass, then exact user-object rules, exact group-object rules, owner rules, organization rules, global rules, and finally deny. At equal specificity an explicit deny wins. Every rule change and user-management action enters `authzAuditLogs`.

The shared scope selector is structured data rather than a free-text `@all`, `@somefield`, or `@someone` expression. It supports include and exclude clauses for identity type, existing organization and cohort, research group, administrative group, and explicit user. A selector has an explicit `match` mode and an empty include list denies by default. Scope has three distinct uses. Content visibility is evaluated dynamically against the current relationship. Workflow assignees are resolved and snapshotted when an instance begins. Notification recipients are resolved and snapshotted when an event occurs. This distinction prevents a later group or adviser change from silently assigning an old task or leaking an old notification.

The initial default capabilities are deliberately narrow. Undergraduates and graduates can use only services made visible to them and can create eligible Coffee Talk applications. Teachers can manage their own explicitly linked research-group content and act on Coffee Talk applications assigned to them. Staff and other accounts receive only administrative groups or rules explicitly granted for their job. Admin and super-admin retain compatible administration responsibilities, but an administrator does not automatically become a teacher or gain unscoped access to every sensitive workflow. Super admin retains recovery capabilities while all normal administration is represented by a scope-aware rule.

## Coffee Talk

Coffee Talk is a real first-delivery application workflow, not a reservation calendar. It is available to signed-in, verified undergraduates and graduate students. It targets a public teacher whose profile marks Coffee Talk as open. The form asks only for topic, purpose, concise research background, expected outcome, preferred format, bounded availability windows, and the applicant’s consent to share the minimum necessary profile/contact context. It accepts no attachments during the first release and does not collect sensitive personal information.

The application record stores the applicant account, target teacher person, optional group context, content fields, contact snapshot, consent choices, current status, timestamps, and a conflict-safe idempotency key. An append-only history stores every transition, actor, preceding and resulting status, timestamp, and permitted note. The first release uses a controlled state sequence: browser-only draft, submitted, under review, needs information, accepted, declined, withdrawn, cancelled, and completed. Accepted applications are scheduled manually by the teacher or an authorized coordinator through an internal note; no availability-calendar, room-booking, or automatic scheduling system is introduced. This preserves the user’s decision to implement Coffee Talk applications while leaving reservation systems as cards only.

Applicants can read only their own applications, supplement an application only after a request for information, and withdraw it while it remains nonterminal. The target teacher can read and decide only applications assigned to their own person record. A scoped coordinator or super administrator can triage, reassign, or correct an application with an auditable reason. A teacher does not see an applicant’s contact detail until the application reaches the appropriate shared stage. Status changes occur through a single server-side mutation that validates the current state, actor capability, ownership, idempotency key, and rate limit before writing history, notification events, and the new state atomically.

The initial anti-abuse policy requires an active verified account and limits unresolved requests per applicant and per teacher. Limits are stored as configuration rather than hard-coded into the interface. The endpoint enforces content length, normalized links, repeated-submit deduplication, and rate limiting. It creates no public aggregate of request count or availability. Coffee Talk content, contact data, availability windows, and decision notes are never placed in analytics payloads, generic error logs, or notification titles.

## Versioned OA, workflow, and notifications

Existing OA forms and reimbursement forms remain readable and usable while the workflow core is introduced alongside them. `approvalWorkflowDefinitions` stores a stable workflow key, immutable published version, source module, submitter scope, and metadata. `approvalWorkflowDefinitionSteps` stores ordered steps, the assignee scope, a limited execution mode, and allowed actions. The initial engine supports sequential approval steps, one successful actor from a task pool, approve, reject, and request-changes. It intentionally excludes condition branches, quorum voting, parallel countersignature, delegation, reminders, escalation, arbitrary scripts, and external-channel side effects.

Starting a new form submission creates an `approvalWorkflowInstance`, version snapshot, active `approvalStepInstance`, one or more `approvalTasks`, and an immutable `approvalEvent` sequence. A task action requires an idempotency key and expected version. It atomically commits the decision, cancels sibling tasks when one actor completes an any-one step, activates the next step, writes events, and creates recipient notification projections. Repeated requests with the same key and payload return the original result. Requests with the same key and different payload return a conflict. Concurrent stale decisions return a stable stale-version result. A missing assignee blocks publication where possible; if a later identity change empties a live task, the instance becomes failed and creates a scoped administrator repair task rather than silently skipping work.

Published definitions and submitted form versions are immutable. Editing an existing template produces a new version and cannot alter labels, required fields, recipients, or steps seen by a historical submission. New workflow instances project compatible states to existing OA fields: running maps to pending, request-changes maps to needs changes, approved maps to approved, and rejected maps to rejected. Old submissions without an instance retain their legacy behavior. An administrator action on a legacy record may lazily wrap it in a clearly labelled one-step legacy workflow; bulk conversion is not required for initial release.

`userNotifications` is the per-recipient in-app notification projection. It contains event identity, recipient, type, minimal title and body, safe deep link, unread/read/archived status, and timestamps. An event-recipient natural key guarantees deduplication. A notification does not grant access: following it invokes the underlying resource authorization again. `approvalMessages` provides the visible workflow time line, with separate submitter-and-approver and approver-only visibility. A future `notificationOutbox` may route the same event to WeChat or a mini program asynchronously. That outbox is deferred; the first release sends only in-app messages and never rolls back a durable business decision because a future external delivery fails.

## Teacher and reviewer integration

Academic-exchange Reviewer and TechDay Reviewer are distinct systems and remain so. Academic Reviewer is a separate credential and session domain with application-material read permissions. TechDay Reviewer is an event-specific direction-based capability that can recommend awards. Existing independent reviewer credentials continue to work.

An academic reviewer account may acquire an optional explicit `mainUserId` link to an AIA teacher account. The link is created by a super administrator or through proof of both active sessions; an email match alone never establishes identity. A teacher can exchange an authenticated main session for a short-lived Reviewer cookie through a dedicated server route. This derives reviewer permission from a current teacher identity without copying the main bearer token into a general cookie. Reviewer sessions and audit entries record whether the action arose from independent reviewer credentials or teacher main identity. Disabling an independent reviewer account revokes independent sessions, while teacher-derived access is separately governed by the current teacher identity and an explicit suspension flag if the institute needs to freeze all review access.

TechDay preserves external author, volunteer, and reviewer accounts. A teacher receives an effective review capability but must be explicitly assigned one or more review directions before seeing or deciding submissions. This capability does not replace an existing author or volunteer role, does not create a TechDay administrator, and does not allow cross-direction access. Where a stable TechDay reviewer identity is required for a decision, an explicitly linked TechDay user is used. The principal resolver refuses to combine a main-site token and an unrelated TechDay token; dual tokens are only combined after the link is verified. Every bind, unbind, login exchange, list, detail view, download, export, and decision gets audit coverage appropriate to the underlying product.

## Safe development clone and demonstration data

All development data operations target only `bold-sandpiper-236`. The source is `clean-swordfish-983`, used only for explicit read-only export. The implementation never adds `--prod` to a command. Before any target write it asserts that the source and target differ, that the target string exactly matches `bold-sandpiper-236`, and that any local environment file does not contain a production deployment value. It validates that `CONVEX_DEPLOYMENT`, `NEXT_PUBLIC_CONVEX_URL`, and `NEXT_PUBLIC_CONVEX_SITE_URL` all refer to the target before local development starts.

The clone workflow creates a private target backup, exports the source with Convex native storage, records checksums and table/file counts without printing document contents, requires an explicit target-name confirmation, and imports only into the target. A post-import export compares table counts, native storage counts, and selected relation integrity. A failed import is rolled back from the target backup. External R2 objects are not present in a Convex export; if the source uses R2, objects are copied read-only from the source to a separate development bucket under the same keys, never synchronized destructively against the source. Target mail, Turnstile, webhooks, signatures, and R2 credentials use development-only values.

The target clone is security-sanitized before AIA testing. It retains required business records and authorized file references but invalidates all main, TechDay, and reviewer sessions; removes email-verification records; disables reachable default credentials and seed functions; and provisions a deliberate development-only administrator account through a standalone controlled operation. The clone does not silently send messages or touch production services. Any subsequent teacher, graduate, group, and Coffee Talk demonstration seed is manually triggered, targets only `dev:bold-sandpiper-236`, uses stable slugs and natural keys, checks existing records before insert, and reports created, updated, and skipped counts. It is never placed in `package.json` scripts or lifecycle hooks.

## Security, failure handling, and observability

The implementation first closes the existing high-severity vulnerabilities before widening access. These include anonymous user creation with privileged roles, unauthenticated role or password operations, client-trusted requester IDs, public full-user record enumeration, public intranet materials, reachable destructive seed/default-credential mutations, and unscoped administrative writes. Password handling is upgraded toward a slow password-based key derivation strategy with a controlled migration path. Sensitive sessions move toward short-lived, revocable, HttpOnly, Secure, SameSite cookies; until a full migration completes, every access endpoint enforces expiry, account status, and server-side session validation. Login and bind routes are rate-limited and protected against cross-origin requests.

The system uses stable application error codes. Relevant examples are `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_FAILED`, `INVALID_TRANSITION`, `STALE_VERSION`, `ALREADY_HANDLED`, `IDEMPOTENCY_CONFLICT`, `ASSIGNEE_EMPTY`, `SOURCE_INVALID`, `ATTACHMENT_FORBIDDEN`, and `IDENTITY_MISMATCH`. Error responses do not disclose another user’s existence, permissions, application content, or attachment metadata. Durable audit entries record actor, action, source, target identity, result, reason where appropriate, timestamp, correlation ID, and credential source. They do not store raw tokens, passwords, full form content, attachments, or personal contact details.

Private attachment and materials access requires both source-resource authorization and a short-lived signed URL. OA, Coffee Talk, Reviewer, and TechDay resources enforce record-level access before file issuance. CSV and other exports escape spreadsheet formulas, limit rows and memory footprint, and create audit events for list, detail, download, and export operations. Sensitive retained data follows a defined retention process: terminal Coffee Talk business fields are minimized after the configured period, sessions and verification artifacts are pruned, and audit records retain the least information necessary for policy and investigation.

## Implementation sequence and verification

Implementation proceeds in six delivery phases. Phase zero prepares the target development deployment, performs a backed-up and verified sanitized clone, aligns environment endpoints, and closes critical authorization exposure. Phase one adds the AIA brand assets, root and Tong Class shells, route helpers and redirects, safe public DTOs, identity fields, group/grant data, the person/group model, and the administrative configuration surfaces. Phase two implements Coffee Talk, in-app notifications, direct object ACLs, history, and explicit demonstration data. Phase three introduces the scope selector and versioned serial workflow engine for OA and reimbursement while keeping legacy submissions compatible. Phase four adds teacher-reviewer linking, TechDay capability checks, strict tags, content bindings, and structured publication aggregation. Phase five considers WeChat, mini-program, reservation-system integration, and a complete institute-local operational deployment after the stable platform core has passed real use.

Each phase has a definition of done. Lint is required, but it is not sufficient because production builds currently ignore TypeScript errors. The implementation uses the repository’s existing static and script checks, adds focused pure-function and integration scripts without modifying package lifecycle scripts, and runs the correct Node/npm versions required by the repository. Browser verification covers desktop and mobile navigation, AIA/Tong Class route compatibility, keyboard accessibility, screen-reader semantics, and public metadata. Authorization verification directly invokes queries and mutations as anonymous, ordinary, disabled, teacher, administrator, super-administrator, reviewer, and unrelated user principals; hiding a button is never accepted as proof.

Migration verification checks idempotence, account identity counts, group membership uniqueness, conflict reports, public DTO field allowlists, zero copied session and verification records, file access expiry, clone table/file counts, and rollback readiness. Coffee Talk verification covers rate limits, all allowed and forbidden state transitions, duplicate submission retries, applicant/teacher/coordinator isolation, notification deduplication, and data-minimized notification content. Workflow verification covers immutable versions, task claiming races, request-changes attempts, task cancellation, scope snapshots, missing-assignee failures, legacy projection, and historical form rendering. TechDay verification covers independent credential compatibility, explicit binding, derived teacher capability, direction restriction, dual-token mismatch rejection, and audit record completeness.

## Acceptance criteria

The AIA delivery is acceptable when the root site shows the approved AIA identity and routes Tong Class into its own first-level context without breaking verified legacy links; existing members resolve to Undergrad identity without changing their access role; public institute and member pages cannot disclose private user fields; no untrusted client can create a privileged account or perform administrative mutations; Coffee Talk can be safely submitted and handled with correct record-level access and history; the target development deployment contains only the authorized sanitized clone plus idempotent demonstration data; and all new scope, workflow, reviewer, and notification paths enforce service-side authorization, auditability, and replay safety. The deferred West Building reservation system remains a truthful card, while WeChat and mini-program work do not start until the in-app platform core has completed these criteria.
