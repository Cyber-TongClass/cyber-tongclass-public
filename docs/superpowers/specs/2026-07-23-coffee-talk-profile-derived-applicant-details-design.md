# Coffee Talk 申请人资料自动带入设计

## 目标

Coffee Talk 申请页的“申请人姓名”“邮箱”“院系 / 单位”“身份”必须直接来自当前登录账户的个人资料，并在页面上只读展示，申请人不能在申请表内修改。

申请人和教师查看历史申请时，这四项资料必须展示申请账户当前的最新资料，而不是提交时的旧快照。

## 资料来源与展示映射

申请人姓名优先使用账户中文姓名；中文姓名为空时使用英文姓名。邮箱使用账户邮箱。院系 / 单位根据账户 `organization` 映射：`pku` 显示“北大通班”，`thu` 显示“清华通班”。身份根据账户 `identityType` 映射为“本科生”“研究生”“教师”或“其他”。

申请页将这四项放在基本信息区域，以只读输入框或只读选择框展示，并提供简短说明，表明资料来自个人账户。其他申请字段（教师偏好、交流主题、可用时间和补充说明）保持现有可编辑行为。

## 提交与数据一致性

客户端提交请求仅包含教师选择及可编辑的申请内容。Coffee Talk 提交 mutation 根据有效会话取得申请账户，服务器端确认教师可用后，仅持久化申请账户关联、教师关联和申请内容；不信任也不接收浏览器提供的姓名、邮箱、院系 / 单位或身份。

申请列表与详情查询根据每条记录的 `applicantUserId` 读取该账户的当前资料，并在返回给申请人和教师的 DTO 中生成展示字段。因此账户资料之后更新时，既有 Coffee Talk 历史申请在两种视图中都会显示最新资料。若关联账户不存在或其学校归属、身份值不受支持，查询以安全的“资料暂不可用”显示降级；提交则拒绝并提示账户资料不完整。

现有申请表记录中的个人资料字段保留在 schema 中以兼容旧记录与避免迁移，但新提交不再写入、读取展示也不再以其为准。

## 变更范围

前端修改 Coffee Talk 申请客户端和表单组件，使其从当前用户资料生成只读资料，并缩小提交 payload。共享类型与客户端 API 将移除可由服务器推导的个人资料输入。

后端修改 Coffee Talk 提交、申请人查询和教师查询：提交时派生可信身份，查询时返回当前账户资料。账户资料 DTO 保持现有组织和身份字段；不新增“院系 / 单位”数据库字段，因为该展示值由组织映射得到。

## 错误处理

未登录状态仍引导登录。正在加载当前账户资料时，表单显示加载状态而不允许提交。学校归属或身份无法映射时，页面显示资料不完整提示并禁用提交；后端也执行同等校验。教师不可用、网络失败及重复提交沿用既有处理。

## 测试与验证

为资料映射建立单元测试，覆盖北大/清华和四种身份。为申请表建立源级或组件测试，确认四项资料只读且不包含变更处理。为后端提交和查询建立测试，确认浏览器伪造的个人资料不会被接受，且查询使用关联账户的最新资料而不是旧快照。最后运行相关测试和 `npm run lint`；如环境可用，再运行构建。
